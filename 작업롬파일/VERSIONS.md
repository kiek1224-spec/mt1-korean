# 작업 롬 버전 기록

빌드 명령은 전부 작업폴더(`디지털 데빌스토리 여신전생 작업`)에서 실행한다.
결과물은 **이 폴더에만** 쓴다. `mt1_kor5b.nes` 와 `mt1_kor5b_v0_base.nes` 는
사용자의 기준선이라 빌더가 덮어쓰지 못하도록 막아 두었다.

```
MT1_VER=v2 MT1_TAG=labels python build_step5b.py
   -> 작업롬파일/mt1_kor5b_v2_labels.nes
```

## ★빌드는 `make.py` 하나로 (2026-09-03)

```
python make.py v12 무슨작업
python make.py v13 진단 --env MT1_UIHOOK=0
```

빌드 -> 검증 7종 -> **기준선 락스텝 대조** -> `VERSIONS.md` 기록까지 한 번에 한다.
**하나라도 실패하면 롬을 `_FAILED` 로 이름을 바꿔 격리**하므로, 폴더에 정상 이름으로
남아 있는 롬은 전부 검증을 통과한 것이다.

락스텝은 사용자 세이브스테이트를 기준선(`v1_base`)과 새 롬에 **동시에** 물려 명령 단위로
돌린다. 갈리는 지점이 곧 원인이다.

**회귀 시험 완료**: `06EB3 13` 을 일부러 `06EB2 14` 로 되돌려 돌렸더니
`check_uistr` 와 락스텝이 **둘 다** 잡고 롬을 격리했다(`vTEST_회귀`).

## v0 과 문제판(2F21163A)의 차이 — 이분 탐색 지도

코드 영역 차이는 **딱 두 갈래**뿐이다.

1. **UI 훅** (`MT1_UIHOOK`)
   - 고정뱅크 `$C13E` 3바이트: `AD 8A 06` → `20 00 6C`
   - 뱅크`$0E` 부팅복사기: 12페이지 → 13페이지
   - 뱅크 `$00 $01 $03 $04 $05 $06 $09 $0C` 에 UI 문자열 이스케이프 제자리 삽입
2. **라벨 전역 치환** (`MT1_LABELS`)
   - 뱅크`$06` 안에서 가나 바이트열을 찾아 제자리 치환

그 외(분할 순서 `$C689`, NMI 업로더 `$C0BF`, 이름 훅 5곳, R7 복원 `$C12A`)는
**v0 에도 똑같이 들어 있다.** 즉 증상의 원인은 위 두 갈래 안에 있다.

## 관측된 증상 (2026-09-02 영상 분석, `2F21163A`)

`Mesen/Avi/mt1_kor5b.avi` 1325프레임 전수 분석.

**증상 A — 하단 상태창 흔들림**: 걸음마다 정확히 한 프레임. 13~14프레임 간격으로 규칙적.
깨짐이 **행 150에서 칼같이 시작**(=스프라이트0 분할선), 행 149까지는 차이 0.0.
창 테두리가 최대 3스캔라인 밀리고 첫 글자줄이 엉뚱한 타일로 그려진다.

**증상 B — 통로의 조각난 형체**: 여러 프레임 지속. 화면 8×8 블록을 롬 CHR 타일
8192개와 2비트 패턴 전수 대조한 결과 **전부 정상 스프라이트 뱅크(`$44`/`$47`) 안의 타일**이었다.
CHR 뱅크 전환·CHR 데이터는 원본과 바이트 단위 동일 → OAM(타일 번호) 쪽 문제.

## 무죄가 확정된 것 (다시 의심하지 말 것)

- **CHR 데이터**: 원본 매퍼76 롬과 바이트 단위 동일. 다른 곳은 1KB 뱅크 4·5(정적 폰트)뿐
- **스프라이트 뱅크표 `$C6BE`** 52엔트리: 뱅크 4·5 를 부르는 엔트리 없음
- **BG 타일셋표 `$C726`** 36엔트리: 원본값 ×2 규칙을 164바이트 전부 준수.
  예외는 타일셋25 의 `b`(CHR-RAM 전환) 하나
- **NMI 글리프 업로더**: 354사이클(3.1스캔라인). 제거해도 증상 그대로

## v5 — UI 훅 재설계: 뱅크 전환 제거 (2026-09-03)

옛 UI 훅은 `$C13E` 안에서 `JSR $C864`(뱅크셋13) / `JSR $C8D5`(복원) 로
**PRG 뱅크를 갈아끼웠다.** 위험한 이유:

- `$C13E` 는 뱅크 `$00 $01 $03 $05 $07 $09` 등 **27곳에서 JSR** 되는 지점이다
- `$C864`/`$C8D5` 는 평범한 서브루틴이 아니다. 스택에서 **자기 리턴주소를 꺼내
  `$15/$16`(또는 `$29/$2A`)에 넣고**, 옛 뱅크셋을 push 한 뒤 `JMP ($0015)` 로 돌아간다.
  `$1F` 값에 따라 스크래치를 갈아탄다(`$C865 LDA $1F / BNE $C89F`)

**해법: 뱅크 전환이 필요 없게 만든다.**
UI 글리프표를 뱅크`$10`의 `$8A00`(뱅크셋13 필요)에서 **PRG-RAM `$6D00`** 으로 옮겼다.
PRG-RAM `$6D00~$7FFF` 4.8KB 가 비어 있었다.

```
옛: $6C1D  LDX #$0D / JSR $C864   ...   $6C49  JSR $C8D5
새: (없음)  — 글리프표가 PRG-RAM 에 있으므로 그냥 LDA $6Dxx,Y
```

곁들여 바뀐 것:
- `COPY` 0xD00 -> **0x1300** (글리프표까지 부팅 때 PRG-RAM 으로 복사)
- 부팅 복사기 125 -> 188바이트. 뱅크`$0E` 의 `$FF` 여유가 4012바이트라 넉넉하다
- 훅 240 -> **232바이트**
- 뱅크`$0F` 레코드 시작이 `$0D00` -> `$1300` (레코드 여유는 충분)

`check_ui.py` 100개 전수 통과.

# ★★원인 규명 완료 (2026-09-03) — `$06EB2` 는 텍스트가 아니라 포인터였다

## 증상
던전 이동 중 통로에 조각난 그림이 뜨고 상태창이 흔들린다. v1/v2 는 깨끗, v4/v5/v6/v7 은 깨짐.

## 찾은 방법 — **락스텝 차분** (`diff_step.py`)
사용자 세이브스테이트를 **두 롬에 동시에 물려 명령 단위로 돌리고**, PC 나 A/X/Y 가
처음 갈리는 지점을 잡는다. 추측이 필요 없다.

```
★128585번째 명령에서 레지스터 갈림 @ $ABDC
   A: A=81   B: A=36
```

## 원인
```
뱅크$03  $ABD4  ADC $AEA1      ; 포인터 하위
         $ABD9  LDA $AEA2      ; ★포인터 상위   v1:$81  /  깨진판:$36
         $ABDE  STA $C1        ; -> $C0/$C1 포인터 완성
   ...   $AE12  STA $0216,Y    ; 그 포인터로 읽은 값을 **OAM 에 쓴다**
         $AE1B  STA $0217,Y
```
`$AEA1/$AEA2` = `0E 81` = **포인터 `$810E`**. 파일 `$06EB2` 가 그 상위 바이트다.
`ui_ko.txt` 첫 줄이 `06EB2 14` 로 **한 바이트 앞에서** 시작해 그걸 덮었다.
망가진 포인터로 읽은 쓰레기가 그대로 OAM 에 들어가 스프라이트가 깨졌다.

**왜 못 봤나**: `$81` 이 가나 「ほ」로 디코드된다. 그래서 구간을 디코드해 보면
`ほの のうりょくを きめます` 로 **텍스트처럼 보인다.** 진짜 텍스트는 `$06EB3` 부터 13바이트.

## 수정

  (UI 문자열 + 라벨 + 패널, v10 기준 158곳)
- 그 구간을 **인덱스 없는 절대주소(`LDA $xxxx`)로 읽는 코드**가 있는지 훑는다.

- 참조 지점이 **역어셈블러가 명령 시작(`code==1`)으로 확인한 자리**인 것만 센다

## ★v42~v50 상세 (2026-09-07 작업 / **2026-09-12 에 사후 복원**)

### 이 절의 신뢰도를 먼저 밝힌다
v42~v50 은 **작업 당시 산문 기록을 남기지 않았다.** 위 빌드로그의 표 한 줄씩이 전부였다.
아래는 2026-09-12 에 **롬끼리 바이트 차분 + 소스에 남은 날짜 주석**으로 되짚은 것이다.

- **근거가 확실한 것**(바이트 위치·코드·문자열이 소스 주석과 정확히 맞은 것)은 그대로 적었다.
- 파생 변경(이스케이프 번호 밀림 등)은 원인을 적고 건수는 생략했다.
- **레코드 뱅크(`$10`~`$1D`)의 대량 차이는 전부 잡음이다.** 메시지가 한 글자만 바뀌어도
  레코드가 통째로 밀린다. 진짜 신호는 **코드 뱅크(`$00`~`$0E`, `$1E`, `$1F`)와 CHR** 뿐이다.
  이걸 모르면 v43·v44·v50 이 "롬 전체를 갈아엎은 것"처럼 보인다.

복원에 쓴 방법 (다시 필요하면 같은 수를 쓸 것):
1. 연속 버전끼리 바이트 차분 -> 바뀐 덩어리를 뱅크·파일오프셋으로 환산
2. 레코드/룩업 뱅크를 걷어내고 코드 뱅크만 본다
3. **가나 표가 아니라 `static_font.txt` 로 디코드한다.** 한글은 정적폰트 1바이트 /
   `$BD <id>` 이스케이프 2바이트 / `$Dn` 공백이라, 가나로 읽으면 전부 뜻 없는 글자가 된다
4. 2바이트짜리 차이는 대개 **텍스트가 아니라 `JSR` 주소**다 (아래 v43·v46·v49 가 전부 그랬다)

## mt1dte / 영어판·스페인어판 대조 (2026-09-03)

### `mt1dte.txt` 는 **배포판에 안 들어갔다**
사용자가 준 `mt1dte.txt` 는 DTE(두 글자를 한 바이트로) 루틴 소스로, `$AF24` 에 훅을 걸고
`$30~$7F` 범위 바이트를 DTE 쌍 색인으로 해석한다. `$07FE/$07FF` 를 임시 저장소로 쓴다.

**그런데 배포된 영어판·스페인어판에는 그 루틴이 없다.** 서명 바이트열을 전수 검색했다:
`STX $07FE` 0곳, `LDX $07FF` 0곳, `CPX #$9D` 0곳.

### 대신 쓴 것: **메시지 포인터 뱅크 확장**
두 판 모두 `$AF24` 를 `JMP $ADA0` 으로 바꿔 놓았다.
```
$ADA0  LDA $BF          ; 메시지 포인터 상위
       CMP #$C0
       BCC (그대로)
       SEC / SBC #$40   ; $C0.. -> $80.. 로 내리고
       R6=$0E, R7=$0F   ; 확장 뱅크로 전환
       LDY $0658 / JMP $AF27
```
즉 **포인터 상위가 `$C0` 이상이면 확장 뱅크로 갈아끼우는** 방식으로 공간을 넓혔다.
우리는 레코드를 뱅크 `$0F~$1D` 로 옮기고 룩업표를 두는 방식이라 접근이 다르다.

### DTE 가 우리 문제를 풀어주지 않는 이유
DTE 는 **바이트 수**를 줄인다. 우리 `stress_name` 문제는 **한 화면에 동시에 필요한
서로 다른 글리프 수**(CHR-RAM 슬롯)라 축이 다르다. 영어판은 라틴 26자가 CHR-ROM 에
그대로 있어 동적 슬롯을 **아예 쓰지 않으므로** 이 문제 자체가 없었다.

다만 DTE 는 우리에게도 쓸모가 있을 수 있다 — UI 문자열은 **제자리 치환이라 원문 길이를
넘을 수 없고**, 빌더가 초과분을 거부한다. 거기서 자리가 모자라면 검토할 만하다.

## 이름 슬롯 재조정 (2026-09-03) — `NDLG` 25 -> 24

`stress_name` 에 **실제로 가능한 조합**을 추가해 재보니, 합성 최악값이 아니라
`악마8 + 아이템8` 에서도 터졌다.

| 이름 풀 | 악마8+아이템6 | **악마8+아이템8** | [합성]악마8+아이템6+마법4 |
|---|---|---|---|
| 27칸 (NDLG=25) | 0건 | **9건** | 24건 |
| **28칸 (NDLG=24)** | 0건 | **1건** | 14건 |
| 29칸 (NDLG=23) | 0건 | **1건** | 6건 |

28칸에서 무릎이다(29로 늘려도 실제 조합은 그대로 1건). 대사는 실측 최대 22칸이라
24 로도 여유 2칸이 남는다. -> **NDLG=24 채택.**

정적 폰트로 더 흡수하는 길은 막혀 있다: CHR 뱅크4/5 에서 정적폰트가 안 쓰는 코드 47개 중
`$00~$09` 는 숫자, `$0A~$23` 은 **창 테두리·커서·화살표 그래픽**, `$5A~$5D` 는 `!?ー・`,
`$5E~$63` 은 `# / . _` 같은 **상태바 기호**다. 실제로 빌 자리가 없다.

### ★남은 확인
`악마8 + 아이템8` 이 실기에서 정말 가능한가? 즉 **아이템 목록이 한 번에 8줄을 보여주는가,
그리고 그때 악마 이름 8개가 같이 떠 있는가.** 아이템 목록이 6줄 이하라면 이 위험은 없다
(`악마8+아이템6` 은 26/28 로 여유 있다).

## 능력치 라벨 5번째 줄 — 악마 화면만 빠져 있었다 (2026-09-03, 사용자 실기 보고)

악마 상태창에서 사람의 `LUK` 자리에 엉뚱한 한글이 떴다.

원인: 능력치 라벨 블록이 **4개**인데(사람 3 + 악마 1), 5번째 줄이 사람은 `う<FF>ん`(운),
**악마만 `ぼうき`(ぼうぎょ, 방어)** 로 문자열이 다르다. `ui_words.txt` 는 가나 바이트열을
전역 치환하므로 문자열이 다르면 통째로 빠진다. 정적 폰트가 가나 타일을 먹었으므로
빠진 자리는 **정적폰트 자리의 엉뚱한 한글**로 뜬다.

```
파일 $0DEAB  81 98 66 6A  = ぼうき   -> DEF   (영어판도 같은 자리를 DEF 로 옮겼다)
```

곁들여: 사람 쪽은 `@0DABA 1 L` `@0DABC 1 K` 로 **양끝만** 박아 화면에 `L K` 로 떴다.
가운데 `<FF>` 까지 덮어 `LUK` 세 글자로 고쳤다(영어판과 동일).

### 재발 방지 — `check_labels.py`
라벨 치환 자리의 **주변 창(±$50)** 에서 **원본과 한 바이트도 안 바뀐 가나 런**을 찾는다.
`가나 코드다`만으로는 안 된다 — **정적 한글이 가나 코드 자리에 살기 때문에** 전부 오탐이 된다.
`안 바뀌었다`가 진짜 신호다. 회귀 시험으로 확인: `@0DEAB` 줄을 빼고 돌리면 잡고 격리한다.

## 표기 불일치 (미결) — `보옥` vs `구슬`
던전 패널(idx6)은 **전용 미니폰트**라 `보옥` 을 쓸 수 있다. 그런데 상태창 라벨(뱅크`$06`
`ほう玉`)은 **정적 폰트 81자 안에서만** 쓸 수 있는데 `보`·`옥` 이 거기 없어 `구슬` 로 두었다.

맞추려면 정적 폰트에서 두 글자를 빼고 `보`·`옥` 을 넣어야 한다.
사용 빈도 하위: **성(2회) 괴(2회)** 령(3) 슈(4) 귀(5) 녀(6).

## ★★새로 발견 — 슬롯 타일이 **게임 그래픽과 겹친다** (미해결)

같은 덤프에서 상태창 초록 상자 테두리가 `$C9`(8칸) `$CB`(15칸) 으로 그려져 있었다.
그 코드들은 **우리 이름 슬롯 범위**다. CHR-RAM 내용을 그려 확인했다:

```
$BF ○   $C1 $C2 $C3 상자 모서리   $C4 P   $C5 :
$C8 ╠   $C9 ─   $CA ╣   $CB │   $CC ◆   $CF 채움블록
```

전부 게임 그래픽이다. 이름 풀에서 **12번째 칸부터** 이 코드에 닿는다
(`TILES[NDLG+12] = $BF`, 13번부터 `$C1~$CF`).

-> **이름 슬롯을 12칸 넘게 쓰면 상태창/목록 화면의 상자 테두리가 한글로 덮인다.**

지금까지 안 터진 이유: 그 코드들의 CHR-RAM 내용은 부팅 때 복사된 **원본 그래픽**이고,
슬롯이 배정되기 전까지는 덮이지 않는다. 파티에 악마가 적으면 12칸을 안 넘는다.

### 새 검사기 `check_slotclash.py`
세이브스테이트를 물려 네임테이블을 훑고, **아직 배정 안 된 슬롯 코드가 화면에 그려져 있으면**
그건 게임 그래픽이라고 판정한다. 화면별로 '몇 칸까지 안전한가'를 낸다.
(옛 빌드 세이브는 PRG-RAM 배치가 달라 무효라 `mt1_kor5b_v*` 만 본다.)

### 선택지
1. `$BF`·`$C1~$CF` 를 슬롯에서 빼기 -> 이름 풀 28 -> **12칸**. 압박 시험이 크게 깨진다
2. 그대로 두고 한계를 문서화 -> 파티에 악마를 가득 채우면 테두리가 깨질 수 있다
3. 실기로 먼저 확인 -> **파티에 악마를 최대한 채우고 상태/목록 화면을 열어 본다**

## v17/v18 — 상태창 상자 테두리 제거 + 병원 문구 (2026-09-03)

★초상화 테두리는 CHR-ROM 코드(`$13 $14 $15`)라 안 걸린다 - 그대로 남는다.

| | 이름 슬롯 안전 한도 |
|---|---|
| 제거 전 | 12칸 (`$BF` 부터 그래픽) |
| 제거 후 | **11칸** (`$BE` 부터) — 한도는 그대로지만 **깨지는 칸 수가 23 -> 6으로 줄었다** |

`$C9`(8칸) `$CB`(15칸) 이 사라진 게 크다. 다만 **한도 자체는 못 올렸다**:
남은 것은 `$BE`(4칸, ◇ 불릿) `$BF`(5칸, ○ 불릿) `$C2 $C3`(블록 머리) `$CD`(1칸).

**즉 목록에 이름이 많으면 여전히 넘친다.** 근본 원인은 CHR-RAM 타일 공간을
게임 UI 그래픽과 나눠 쓴다는 것이고, 남은 선택지는 둘뿐이다:
1. 불릿(`$BE $BF`)까지 지운다 -> 한도 11 -> **14칸**. 여전히 부족
2. 아이템·마법 이름을 **정적 폰트 음절 위주로 다시 다듬어** 슬롯 수요를 줄인다

   실측: 아이템 64개 = 고유음절 136종 중 **77종이 정적 밖**, 마법 36개 = 54종 중 28종

## ★v19 — 영어판이 사람/악마 화면을 다르게 만든 이유 (2026-09-03)

사용자가 영어판 두 화면의 UI 디자인이 다른 걸 발견해 준 것이 결정적이었다.
레이아웃 블록별로 상자 코드를 세어 보니 **의도적인 설계**였다:

| 블록 | 원본 | 영어판 | 우리(v19) |
|---|---|---|---|
| 사람 블록1 | 23개 | **0개** | **0개** ✔ |
| 사람 블록2 | 15개 | **0개** | **0개** ✔ |
| 사람 블록3 | 0개 | 0개 | 0개 ✔ |
| 악마 블록 | 21개 | **21개 유지** | **21개 유지** ✔ |

**이유가 명확하다**: 사람 화면은 아이템 목록 + 마법 목록이 **같이** 떠서 이름이 많고,
악마 화면은 마법 목록 하나뿐이라 여유가 있다.

그리고 영어판은 빈칸 타일(`$59`)이 아니라 **`$FF`**(아무것도 안 그림)로 바꿨다.
레이아웃이 원래 `$FF` 로 빈 칸을 채우므로 그게 이 루틴의 '없음'이다.
```
원본  FF FF F5 C9 0E 0B F4 FF        <- F5 ─ 반복 F4
영어  FF FF FF FF 0E 0B FF FF
```
v18 에서 4블록 전부를 `$59` 로 지웠던 것을 **영어판과 바이트 수준으로 일치**시켰다(38칸).

### 남은 걸림돌과 정확한 숫자
사람 블록에 남은 슬롯 범위 코드:
```
$BE  8개 (이름풀 11)  = ※ 모양 불릿
$BF 10개 (이름풀 12)  = ○ 불릿
$C2  2개 (이름풀 14)  \ 블록 머리 `C2 D4 0E 08 C3` = 초상화 테두리
$C3  2개 (이름풀 15)  /
$C4  2개 (이름풀 16)  = P (Pts.)
$CE  2개 (이름풀 26)
```
-> **사람 화면 이름 슬롯 안전 한도 11칸 / 풀 28칸.**

### 더 올리는 법 (아직 안 함 - 겉모습이 바뀐다)
`$BE`·`$BF` 불릿을 **CHR-ROM 의 ◆(`$22` 또는 `$23`)** 로 옮기면 된다.
둘 다 정적 폰트 범위($24~$59, $64~$7F) **밖**이라 원본 그래픽이 그대로 살아 있고,
`TILES`(슬롯)에도 들어 있지 않다. 옮기면 한도가 **11 -> 14칸**이 된다.
영어판 화면도 `◆` 다이아몬드 불릿이라 오히려 그쪽에 가까워진다.

그 위(`$C2 $C3`)는 **초상화 테두리**라 건드리면 안 된다(사용자 지시).

### 그래도 근본 한계는 남는다
LV60 세이브 화면은 이름이 ~15개 뜨고 고유 음절이 30~50종이다. 한도를 14 로 올려도 모자란다.
**남은 진짜 선택지는 아이템·마법 이름을 정적 폰트 음절 위주로 다시 다듬는 것**뿐이다.
실측: 아이템 64개 = 고유음절 136종 중 77종이 정적 밖 / 마법 36개 = 54종 중 28종.
종족 20개가 정적 2음절이라 **슬롯을 0칸 쓰는 것**이 그 방식의 증명이다.

## ★CHR-RAM 확장(매퍼195) 프로브 — 성공 (2026-09-03)

### 이전 결론을 뒤집는 이유
이전 세션은 195 를 "용량 이득 없어 불채택" 했다. **그때 본 것은 `$80~$FF` 쪽**이고 그건 맞다.
블리터가 그릴 수 있는 코드는 `$00~$CF` 뿐이라 RAM 을 키워도 **코드 수는 안 늘어난다.**

지금 노리는 것은 다르다:
```
지금(191) : 코드 $00~$7F = CHR-ROM 뱅크4/5 = 정적 폰트 81칸 **고정**
            코드 $80~$FF = CHR-RAM 2KB     = 슬롯 52칸 (가변)
195       : 코드 $00~$FF **전부 CHR-RAM 4KB** -> 81칸이 고정에서 **가변**으로
```
아이템·마법 목록 화면이 요구하는 30~50종을 감당할 수 있게 된다.

### 프로브 `build_m195_test.py` -> `작업롬파일/mt1_m195_test.nes`
1. CHR 128KB -> 256KB, 뱅크 `$00~$03` 을 `$80~$83` 으로 이설 (195 는 그 4뱅크가 곧 RAM)
2. BG표 `$C726`: `a=$00->$80`, `a=$02->$82` (35개 타일셋 x 4뱅크 내용 동등성 확인, 불일치 0)
3. **타일셋25**: `a=$04->$02`(RAM 2,3), `b=$80->$00`(RAM 0,1)
4. 헤더 매퍼195 / CHR 256KB
5. 부팅 업로드 61바이트를 뱅크`$0E $8200` 에, 정적폰트 2KB 사본을 `off $1800`(전부 비어 있었다) 에
   - `$804F` 의 `LDA #$80 / STA $A001` 를 `JSR $8200` 으로 바꿔 끼움
   - ★기존 부팅 복사가 R4/R5 에 `$80/$81` 을 쓰는데 195 에선 그게 **진짜 ROM 뱅크**라
     복사가 통째로 무시된다. `$00/$01` 로 고쳐야 한다 (프로브에서 실제로 걸렸다)

### 검증 결과
```
부팅 600프레임 통과. VRAM 쓰기 6147회 (기준선과 동일)
CHR-RAM 쓰기 4096회 - 4KB 전부 채워짐
  페이지2,3 (코드 $00~$7F) == 정적폰트  일치
  페이지0,1 (코드 $80~$FF) == 원래것    일치
같은 세이브 화면 픽셀 비교: 차이 0 / 245760  완전 동일
쓰기 경로 시험: 코드 $00~$3F/$40~$7F/$80~$BF/$C0~$FF 네 구간 전부 RAM 읽기·쓰기 OK
              (191 에서는 $00~$7F 쓰기가 8/8 무시됨)
```

### 이미 있던 발판
부팅 CHR-RAM 채우기가 **이미 있다** (뱅크`$0E $8013~$804D`):
vblank 2회 대기 -> R4/R5 설정 -> PPU `$1800` -> CPU `$9000`(뱅크`$0E` off `$1000`
= CHR 뱅크`$06,$07` 의 PRG 사본)에서 2KB 복사. 여기에 한 덩이 더 붙인 것뿐이다.
뱅크`$0E` 는 `$0200~$0FFF`(3584바이트)와 `$1800~$1FFF`(2048바이트)가 전부 비어 있다.

### 남은 일 (진짜 이득을 보려면)
프로브는 "정적 폰트를 RAM 에 올려도 화면이 같다"까지다. **가변으로 쓰려면** 더 필요하다:
1. 정적 폰트 81칸을 **슬롯 풀에 합친다** -> 가변 칸 52 -> **134칸**

2. 인코더에서 정적/동적 구분을 없앤다 (`STATIC` 경로 제거, 전부 슬롯 배정)
3. 화면 전환 때 **묶음 업로드**가 필요하다. 50음절 x 16 = 800바이트 -> 화면 끈 상태면 한 프레임
4. 업로드 전에 화면이 뜨면 전부 빈칸이 된다 -> 순서 보장이 필요

## v20 — 유미코 화면 잔여 테두리 (2026-09-03, 실기 보고)

나카지마 화면은 깔끔했는데 **유미코 화면만 아래에 초록 줄**이 남았다.
원인: 블록2 의 바닥 테두리 `F6 F9 .. F7` 이 `$0DCE8` 에 있는데
내 범위가 `$0DC7C~$0DCE8`(끝 제외)이라 **한 바이트 차이로 빠졌다.**

### 범위로 잡는 방식을 버렸다
영어판이 **실제로 지운 자리를 그대로 목록화**해 박아 넣는다(41곳).
뽑는 법: v3 에서 상자코드이고 영어판에서 `$FF` 인 뱅크`$06` 주소 전부.
```
BOXCLEAR = [0x0DAE6, 0x0DAE7, 0x0DAEA, 0x0DAFC, ... 0x0DCE8, 0x0DCE9, 0x0DCEC]  # 41곳
```
빌더가 `assert rom[a] in BOXCODES` 로 목록의 정합성을 매번 확인한다.

**검증**: 뱅크`$06` 에 남은 상자코드가 영어판 91개 / 우리 91개, **주소까지 동일**.

## ★전투 제어코드 확정 (2026-09-03, 역어셈블 + 영어판 대조)

### 표
| 코드 | 뜻 | 추가 바이트 |
|---|---|---|
| `$Dn` | 빈칸 n개 | 0 |
| `$En` | **n 프레임 대기** | 0 |
| `$FD` | 개행 | 0 |
| `$FE` | 종료 | 0 |
| `$FF` | 버튼 대기 | 0 |
| `$62` | 「。」 일본어 마침표 (영어판은 `$61` = `.`) | — 글자다 |

### `$En` 을 어떻게 확정했나
```
$C202  CMP #$E0 / BNE $C213
$C206  LDA $0590,X / AND #$0F / JSR $C2C6     ; 하위니블을 인자로
$C2C6  CMP #$00 / BEQ (아무것도 안 함)
       STA $0602 / JSR $C5A1 / DEC $0602 / BNE   ; 니블 횟수만큼 반복
$C5A1  LDA #$00 / STA $08
       LDA $08 / CMP #$FF / BNE (제자리)          ; ★NMI 가 $08 을 $FF 로 세울 때까지
       INC $0C / RTS                              ;   = 한 프레임 대기
```
NMI 출구 `$C114 LDA #$FF / STA $08` 이 짝이다. 즉 **`$En` = n 프레임 뜸 들이기**.

전투 문장 끝의 `<EF><E8><FE>` = 15프레임 + 8프레임 대기 후 종료 = **연출 타이밍**이다.
지우면 문장이 눈 깜짝할 새 지나간다. 영어판도 이 코드들을 **그대로** 두었다.

뱅크`$0C` 사용 분포: `$E5`x1 `$E6`x1 `$E8`x10 `$EB`x2 `$EE`x1 **`$EF`x50**

### 새 검사기 `check_ctrl.py`
제자리 치환 127개가 **`$E0` 이상 제어코드 구성을 그대로 보존했는지** 본다.
`$Dn`(빈칸)은 한국어 띄어쓰기가 달라 당연히 바뀌므로 **제외**한다.
`make.py` 검사 목록에 넣었다(이제 9종).

## v22 — 전투 문장 다듬기 (2026-09-03)

### 가장 큰 문제: 조사가 고정이었다
전투 문장은 **이름 뒤에 붙는 꼬리 조각**이다. 그런데 번역이 `은 도망쳤다` 처럼
조사를 박아 놔서 이름의 받침에 따라 틀린다:
```
전: 헤케트은 도망쳤다   노움은 도망쳤다      <- 앞쪽이 틀렸다
후: 헤케트 도망쳤다     노움 도망쳤다        <- 조사를 뺐다
```
한국어 게임 로그에서 주어 조사를 생략하는 건 자연스럽다. `의`(`의 공격!`)처럼
**교체가 없는 조사는 그대로 둔다.**

## 전투 이상 조사 (2026-09-03) — 재현 실패, 대신 `$F2` 의 정체를 확정

### 먼저 사실 정정: 본선은 아직 **매퍼191**이다
`v20~v22` 는 전부 매퍼191 / 385KB 다. `mt1_m195_test`(513KB)는 **프로브 하나뿐**이고
그것도 **v20 에서 만든 것**이라 v21(`ひき`)·v22(전투 문장)가 안 들어 있다.
매퍼195 본작업은 시작하지 않았다.

### 세이브스테이트로 재현 시도 -> 세 롬이 동일하게 동작
사용자 전투 세이브(`mt1_m195_test_3.mss`)를 물려 150만 명령 돌렸다.
```
m195 프로브(v20)   프레임 144  대기루프 795802  루프탈출 133  $C13E 0회
v22 (191)         프레임 144  대기루프 795802  루프탈출 133  $C13E 0회
v1_base (기준선)    프레임 144  대기루프 795802  루프탈출 133  $C13E 0회
```
**기준선까지 완전히 같다.** 그 상태는 `$C5F2`(= `$0B` 비트0 이 내려갈 때까지 프레임 대기)
에서 입력을 기다리는 정상 상태이고, `$C13E` 는 아예 안 불린다.

### 검증한 것 (전부 이상 없음)
- `$E0` 이상 제어코드: 제자리 치환 127개 **전부 보존** (`check_ctrl`)
- 인자를 먹는 제어코드가 치환 구간 **안에** 들어간 곳: **0건**

### ★★`$F2` 는 경로마다 다르게 동작한다
`PARAMS` 표는 `$F2` 가 인자 1개를 먹는다고 적고 있다. 근거는 **대사 엔진** 핸들러다:
```
$B004  INY / LDA ($BE),Y / CLC / ADC $068F / STA $068F / INC $0658 x2
       -> $F2 <n> = $068F 에 n 을 더하고 2바이트 전진
```
그런데 레벨업 메시지에 그 규칙을 대면 문장이 깨진다:
```
인자 1개로 읽으면 : なかじまの [F2+75]よさ[F2+69]゛ あがった!     <- 깨진다
인자 0개로 읽으면 : なかじまの [F2]つよさ[F2]が あがった!          <- 맞다
```
즉 **레벨업 문자열 경로에서는 `$F2` 가 인자를 안 먹는다.** `PARAMS` 는 대사 엔진 전용이다.
(영어판은 아예 그 `$F2` 들을 글자로 덮어써 버렸다 — 「Strength」가 그 자리를 먹는다.)

-> 우리 치환이 `$F2` **바로 뒤**에서 시작하는 20곳은 **정상**이다. 거짓 경보였다.

(예: 데미지 숫자가 이상한가 / 문장이 아예 안 뜨는가 / 특정 기술에서만 그러는가)와
그 순간의 세이브스테이트가 있으면 락스텝으로 바로 잡을 수 있다.
